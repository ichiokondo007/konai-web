# 電球操作 API(Express + TypeScript)実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** side3 上の `http://side3:3000/lights/living1/state` に curl で `{"state":"ON"}` を送ると Hue 電球が点き、`GET /lights/living1` で現在状態が返る API を Docker で稼働させる。

**Architecture:** `api/` に Express 5 + TypeScript の 3 層構成(HTTP 層 → `LightService` → `LightGateway` インターフェース → `Zigbee2MqttGateway`)を作る。ゲートウェイは `zigbee2mqtt/+` を購読し、`set` / `get` を発行してから `zigbee2mqtt/<name>` の次の 1 メッセージを待つ同期型。compose に `api` サービスを追加し、side3 で `git pull && docker compose up -d --build` で更新する。

**Tech Stack:** Node.js 22、TypeScript 5(strict、ESM)、Express 5、mqtt.js 5、tsx、Vitest、supertest、aedes(テスト用 MQTT ブローカー)、Docker Compose

**Spec:** `docs/superpowers/specs/2026-10-26-light-api-design.md`

## Global Constraints

- 作業は worktree + ブランチ `feature/light-api`。完了後 main にマージ。設計書・計画書は main が正本
- アプリのルートは `api/`。`package.json` は `"type": "module"`、`tsconfig.json` は `module: NodeNext`、`strict: true`。ソース内の相対 import は `.js` 拡張子付き(`import { loadConfig } from "./config.js"`)
- 依存のメジャーバージョン: `express@5`、`mqtt@5`、`typescript@5`(7 系は使わない)、`tsx@4`、`vitest@5`、`supertest@7`、`aedes@1`、`@types/node@22`、`@types/express@5`、`@types/supertest@7`
- 入力検証ライブラリ、構造化ログライブラリは入れない。ログは `console.log` / `console.warn` / `console.error`
- 環境変数: `PORT`(既定 3000)、`MQTT_URL`(必須)、`MQTT_BASE_TOPIC`(既定 `zigbee2mqtt`)、`LIGHTS`(必須、カンマ区切り、空要素は不正)、`DEVICE_TIMEOUT_MS`(既定 5000)
- エラー応答の形は常に `{"error":{"code":"...","message":"..."}}`。code と HTTP の対応: `INVALID_REQUEST` 400、`LIGHT_NOT_FOUND` 404、`MQTT_UNAVAILABLE` 503、`DEVICE_TIMEOUT` 504、`INTERNAL_ERROR` 500
- `PUT .../state` の body は `{"state":"ON"}` または `{"state":"OFF"}` のみ。小文字や `TOGGLE` は 400
- MQTT トピック: 購読 `<base>/+`、操作 `<base>/<name>/set` に `{"state":"ON"}`、取得 `<base>/<name>/get` に `{"state":""}`、応答は `<base>/<name>`
- Zigbee2MQTT 側の電球 friendly name は `living1`(現在の `hue-bulb-1` から変更する。Task 7)
- side3 の操作は ssh 経由。side3 上でファイルは編集しない
- 各タスクの最後にコミットする。コミットメッセージは日本語、prefix は `feat:` / `test:` / `docs:` / `chore:`

## Review Focus

1. 存在しないパスや未対応メソッド(`DELETE /lights/living1` など)でも Express 既定の HTML ではなく JSON の 404 を返すこと(Task 3 のテスト `unknown route returns JSON 404`)
2. body が壊れた JSON のとき、body パーサーの既定エラーではなく `INVALID_REQUEST` の 400 で返ること(Task 3 のテスト `malformed JSON body returns 400`)
3. `living1` を待っている間に `living2` の状態メッセージが届いても、`living1` の待ち受けが解決しないこと(Task 4 のテスト `ignores messages for other lights`)
4. タイムアウト後に遅れて応答が届いても、unhandled rejection やクラッシュにならず無視されること(Task 5 のテスト `late response after timeout is ignored`)
5. 待ち受け中に `close()`(終了処理)が呼ばれたら、待ち受けを `MqttUnavailableError` で即時に却下し、HTTP リクエストが終了処理を妨げないこと(Task 5 のテスト `close rejects pending waiters`)

### Task 4: `Zigbee2MqttGateway` の基本動作(set / get / タイムアウト / 未接続)

**Files:**
- Create: `api/src/zigbee/Zigbee2MqttGateway.ts`
- Create: `api/test/helpers/testBroker.ts`
- Test: `api/test/Zigbee2MqttGateway.test.ts`

**Interfaces:**
- Consumes: Task 2 の `LightGateway`、`LightState`、`MqttUnavailableError`、`DeviceTimeoutError`
- Produces:
  ```ts
  export interface Zigbee2MqttGatewayOptions {
    url: string;
    baseTopic: string;
    timeoutMs: number;
    reconnectPeriodMs?: number;   // 既定 1000。mqtt.js の reconnectPeriod に渡す
  }
  export class Zigbee2MqttGateway implements LightGateway {
    constructor(options: Zigbee2MqttGatewayOptions);
    connect(): void;                 // mqtt.connect を呼び、connect / message / close / error ハンドラを登録する。connect ごとに `${baseTopic}/+` を購読し、connect / close / error 時に console.log / console.warn で 1 行出す
    close(): Promise<void>;          // client.endAsync()。Task 5 で待ち受けの却下を追加
    isConnected(): boolean;          // client?.connected === true
    setState(name, state): Promise<LightState>;   // 待ち受け登録 → `${baseTopic}/${name}/set` に JSON.stringify({ state }) を publish
    getState(name): Promise<LightState>;          // 待ち受け登録 → `${baseTopic}/${name}/get` に '{"state":""}' を publish
  }
  ```
  内部: `waiters: Map<string, Set<{ resolve; reject; timer }>>`(キーは電球名)。`message` ハンドラはトピックが `${baseTopic}/${name}` の形(スラッシュをちょうど 1 つ含む)のときだけ処理し、`JSON.parse` して `state` が `"ON"` か `"OFF"` のものを `LightState`(`receivedAt: new Date()`、`brightness` は数値のときのみ)にしてその名前の全 waiter を resolve する。解析できない / `state` が不正なら `console.warn` して無視。`setState` / `getState` は `isConnected()` が false なら即 `MqttUnavailableError` で reject。タイムアウトは `setTimeout(timeoutMs)` で `DeviceTimeoutError(name, timeoutMs)`。resolve / reject のどちらでも timer を clear し waiter を Set から外す
- Produces(`test/helpers/testBroker.ts`):
  ```ts
  export interface TestBroker {
    port: number;
    url: string;
    publish(topic: string, payload: string): Promise<void>;      // テスト側が Zigbee2MQTT のふりをして応答を流す
    nextPublish(topic: string): Promise<string>;                 // クライアントがそのトピックに次に publish した payload を返す
    close(): Promise<void>;
  }
  export function startTestBroker(port?: number): Promise<TestBroker>;  // aedes + net.createServer をポート 0(省略時)で listen
  ```
  `publish` は aedes の `broker.publish({ topic, payload, qos: 0, retain: false })`。`nextPublish` は `broker.on("publish", (packet, client) => ...)` で `client` が null でなく(ブローカー自身の発行を除く)`packet.topic` が一致した最初の payload で resolve する
